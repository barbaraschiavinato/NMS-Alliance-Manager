# AGENTS.md

Guidance for AI coding agents working in this repository.

## Commands

```bash
npm install
npm run dev     # Next.js dev server (Turbopack) on http://localhost:3000
npm run dev:local   # Same, with the local development accounts (no Google)
npm run dev:test    # Same, with the 9 fixed test accounts and populated data in data-test/ (copied from fixtures/test-data/)
npm test        # All tests (Vitest)
npm run test:watch      # Same, in watch mode
npm run test:coverage   # Same, with a coverage report in coverage/ (git-ignored)
npm run lint    # ESLint
npm run format  # Prettier (write)
npm run format:check  # Prettier (check only)
npm run build   # Production build (also runs the TypeScript type check)
```

All tests live in `tests/`, never next to the code, and mirror the source: `tests/lib` (pure logic), `tests/stores` (`*-store.ts`, plus `test-data.test.ts`), `tests/api` (route handlers), `tests/components` and `tests/pages` (React, with jsdom). `tests/setup.ts` moves each test file into a fresh temporary directory, so the stores write to an isolated `data/`, and clears auth, Blob and data-folder variables. API tests mock only `@/auth` (`tests/helpers/auth.ts`, `signInAs`), so the real `getCurrentMember` runs. Seed data with `tests/helpers/members.ts`. Component test files start with `// @vitest-environment jsdom` and render with `renderWithLocale()` (`tests/components/helpers.tsx`) or `renderPage()` (`tests/pages/helpers.tsx`). Before adding a test file, check whether one already exists for the module.

**`src/lib/nms-core/` is vendored third-party code: don't write tests for it** (it is excluded in `vitest.config.mts`). When you change behaviour, update or add the matching tests. Verify changes with `npm test`, `npm run lint` and `npm run build`. CI (`.github/workflows/ci.yml`) runs lint, tests with coverage (failing below the thresholds in `vitest.config.mts`) and the build on every push to `main` and every pull request, plus `npm run audit:prod`.

Formatting uses Prettier (`prettier.config.mjs`, `.prettierignore`), wired into ESLint through `eslint-config-prettier`. The existing code was never formatted with it, so don't run `npm run format` on the whole repo inside an unrelated change: format only the files you create or edit (`npx prettier --write <files>`). Markdown, CSS in `src/styles/`, `public/`, `data/` and `nms-core` are ignored.

Local auth needs `.env.local` (see `.env.example`). The quick option is `LOCAL_AUTH=true` (`npm run dev:local`): the login screen then offers development accounts (`src/lib/auth/local-auth.ts`: admin, moderator and regular user, with editable profiles), each pre-approved with a complete profile, no Google variables are needed, and storage is forced to local files in `data/`. `npm run dev:test` selects the test set (`LOCAL_AUTH_SET=test`): nine fixed accounts, one per role and specialty, with a profile that cannot be edited and is reset on every login. Its data lives in `data-test/` (`NMS_DATA_DIR`), recreated on every start from `fixtures/test-data/` (members, missions, stations, task status and messages with fixed ids); `tests/stores/test-data.test.ts` checks that the fixtures load with the real store readers. Each login button has `data-testid="local-login-<email>"`. `isLocalAuthEnabled()` ignores the flag when `NODE_ENV=production` or `VERCEL` is set, so it never affects a build or deploy. For real Google login, set `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`, `AUTH_URL=http://localhost:3000/api/auth`, `ALLIANCE_ADMIN_EMAIL`. If any of these is missing (and local mode is off), pages render the login screen listing what's missing; the list comes from `getMissingAuthConfiguration()`. The configured admin email is auto-approved.

## Architecture

Next.js 16 App Router + React 19 + TypeScript, Auth.js v5 (Google OAuth), Tailwind v4 plus hand-written CSS in `src/styles/`. The app coordinates a No Man's Sky alliance: missions, discovered stations, planets, members, messages, help requests, leaderboard.

### Persistence: JSON files, local or Vercel Blob

`src/lib/` is grouped by domain: `almanac/`, `auth/`, `members/`, `messages/`, `missions/`, `navigation/` (detail links, view switching, pagination sizes), `notifications/` (Taxi and user alerts), `planets/` (addresses, galaxies, system status), `stations/`, `storage/` (Blob and local data paths), `utils/`, plus `translations/` and the vendored `nms-core/`. Put new modules in the matching folder instead of the root of `src/lib/`.

There is no database. Each domain has a `*-store.ts` module in its `src/lib/` folder (`missions/store.ts` for missions, `members/access-store.ts` for members and alliance settings, `stations/stations-store.ts`, `almanac/almanac-store.ts`, `messages/private-messages-store.ts`, `planets/planet-system-status-store.ts`, `notifications/*-notifications-store.ts`). Each one reads and writes a whole JSON document:
- `getBlobAuthOptions()` (`src/lib/storage/blob-config.ts`) decides the backend. It returns Blob options when `NMS_STORE_ID`/`BLOB_STORE_ID` (OIDC on Vercel) or `NMS_READ_WRITE_TOKEN`/`BLOB_READ_WRITE_TOKEN` is set, and otherwise returns `null`, which means the local filesystem under `data/` (gitignored). On Vercel without a store it throws, so production never writes to the Function's filesystem.
- Blob files live under `alliance-manager/*.json`, are `access: "private"`, and are written with `allowOverwrite: true` (read-modify-write, with no locking).
- Read functions run **migrations on read**. For example, `missions/store.ts` turns legacy email/name fields into member `publicId` references and normalizes status/priority, then writes the result back when it changes anything. When you change a stored shape, add the migration here; don't assume existing data matches the new types.
- Derived fields (owner/assignee names, etc.) are stripped before writing. `serializeMission` (`src/lib/missions/mission-view.ts`) resolves them again from members when responding.

### Auth and authorization

- `src/auth.ts` configures Auth.js (Google, plus a `local` credentials provider when `LOCAL_AUTH` is active). Server code calls `getCurrentMember()` (`src/lib/auth/authorization.ts`), which also **registers the member on first login** (`registerMember`). It returns `null` for offline, blocked or pending members unless the caller passes `allowPending`/`allowBlocked`.
- Roles are `user < moderator < admin`, checked with `hasRole(member, "moderator")`. Membership status is `pending | approved | blocked`; operational endpoints require `approved`.
- **Simple view:** when an admin or moderator enables `simpleView`, `getCurrentMember` downgrades `role` to `"user"` (the real role is kept in `displayRole`), so the server enforces user-level permissions too.
- Every API route handler (`src/app/api/**/route.ts`) does its own session and role checks (`runtime = "nodejs"`, `dynamic = "force-dynamic"`). Mission creation has specialty-specific rules (Ranger/Explorer/Builder) in `src/app/api/missions/route.ts`.
- "Offline members" are profiles that moderators create for players without a Google login (`members/offline-members.ts`, `createOfflineMember`).

### Pages

Each `src/app/<section>/page.tsx` is a thin server component. It loads access data, handles missing config, the login screen and pending approval, then renders a client component from `src/components/pages/` (e.g. `MissionDashboard`). Client components fetch from `/api/*`. `/` redirects to `/stations`. UI is built from cards in `src/components/cards/`, which have `simple` and `extended` variants. `src/app/guide/` is a user guide that renders live example components, which live in `src/components/guide/`. Keep `src/app/` for routes only (`page.tsx`, `layout.tsx`, `route.ts`, `not-found.tsx`): put any other component or helper in `src/components/` or `src/lib/`.

### NMS domain

- Station details live at `/stations/[id]`, with an encoded composite `ownerId:PORTAL:galaxy` ID (no new stored field). Changing a coordinate or owner changes the URL; navigate to the updated URL after an edit and to `/stations` after deletion.
- Decode the station route ID exactly once in `parseStationId`: this Next.js version can supply encoded separators in route params. Reject malformed and double-encoded IDs rather than decoding repeatedly.
- The list and detail routes share `components/pages/stations-route.tsx` for authentication, membership gates and station visibility. Return 404 for invalid, missing or inaccessible station IDs.
- Links to a specific station from Planets, Missions, Messages and Taxi use `stationDetailHref`, not `/stations?search=...`. Resolve the actual registered station and galaxy, including its current owner; private-message links are derived by the API, never persisted. Hide links for missing/inaccessible message stations and retain taxi meeting snapshots as text when the station no longer exists. Keep member-wide station searches and create-station links unchanged.
- Station detail links carry a `from` origin (`planets`, `missions`, `messages`, or `taxi`). Validate it against `detailOrigins`; never accept arbitrary return URLs. The back link uses the matching translated label and section destination, defaulting to Stations for direct links or invalid origins. Preserve the origin when station edits change the composite URL; do not rely on browser history for the back destination.
- Station details embed `HelpRequestsPage` with `systemScope` as the final block, after system/planets. Include help requests for every planet in the same system and galaxy, with existing replies and authorization for reply/delete actions. Hide the section when no requests match (including after deletion), but display loading failures explicitly. Reuse the board's cards/actions without duplicating the sidebar, header, hero or main landmark.
- `DetailBackLink` and `DetailSection` provide reusable detail navigation/blocks. Station details show the existing station card/actions, scoped `MissionDashboard`, then embedded `PlanetsPage`. Scope mission association by galaxy and the last eleven portal glyphs, not station ownership or a text search.
- In station details, the station card is always full width, not a grid item. Hide redundant station links in the embedded system/planet cards, the station detail-link action, and "Open associated missions"; retain eligible mission creation and individual mission opening. In the main station list, place the blue (`#6cb4ff`) detail-link action after the associated-mission icon and before deletion. Keep Delete last, after Edit and any Notes action, in both station card variants.
- Station cards matching the configured alliance hub (`alliance.portalCode` and `alliance.galaxy`, ignoring the first portal glyph and letter case) show a red **Alliance hub** ribbon (Italian: **Hub alleanza**) in the same top-left position as New. The hub ribbon replaces New, regardless of station age or associated missions, in both card variants and all station/detail contexts. Derive this from current alliance settings, never persist a hub flag; invalid or absent hub codes match nothing.
- **Associated missions in station details:**
  - This is an explicit visibility exception: show all associated specialties and assignees through `/api/missions?stationPortal=...&galaxy=...`, after checking approved membership and access to the registered station. Keep the default mission feed and the main Missions page's visibility rules unchanged.
  - For regular users, show **Claim** only on unassigned missions targeting their exact specialty or `all`, using the existing server-side profile and claim checks. Do not offer direct claims for `explorer_builder`, even to Explorers or Builders: the current claim endpoint does not support it.
  - Missions targeting other specialties or assigned to another member remain visible without operational actions.
  - On the current member's assigned missions, show **Start** when pending, **Complete** when in progress (enabled only when the required tasks are complete), and **Reopen** when completed.
  - Moderator/admin management actions remain unchanged. Simple view enforces regular-user permissions, including for moderators and admins.
  - Omit the mission block when empty. Show all associated cards directly, without tabs, search, pagination or the list footer.
- `loadPlanetDestinations` in `lib/planet-destinations.ts` is shared by Planets and station details. Scope its input before Almanac lookups; embedded planet lists must not overwrite the global sidebar planet counter.
- Mission details live at `/missions/[id]` and reuse the station-detail route loader and page composition. Their block order is selected mission (one full-width card), linked station (full width), associated missions, system/planets, then optional system help requests. Keep the selected mission in the associated list too; both copies share dashboard state so actions and progress stay synchronized.

Omit the separate selected-mission card and its "Mission" heading, but retain the selected mission in the associated list and its ID for scoped loading, permissions and deletion handling. `from` controls back navigation only, not layout: a mission card opened from station details (`from=stations` without `source=station-card`) retains the normal selected-mission-first layout. Other entries and ordinary station details keep their existing block order.

Keep `from` for direct-link fallback and `source=station-card` for the explicit layout exception; neither replaces the contextual return destination. Only allow supported internal section/detail paths, reject external or malformed return targets, and fall back to the section for direct links or self-returns. - Missions model and validation: `src/lib/missions/missions.ts`. Member types and friend-code validation: `src/lib/members/member-types.ts`. Demo seed: `src/lib/missions/seed.ts`.
- System addresses are 12 hex glyphs plus a galaxy index (0–255) (`planets/galaxies.ts`, `planets/planet-addresses.ts`, `components/shared/portal-address-field.tsx`). Glyph images are in `public/glyphs/`.
- Addresses are verified against the external NMS Almanac API (`almanac/almanac-lookup.ts`). Respect the service's `RateLimit`, `RateLimit-Policy`, and `Retry-After` headers; quotas are weekly, not the former 500 requests/hour. On a 429, `almanac/almanac-rate-limit.ts` pauses every Almanac request of that server instance until `Retry-After` has passed (60 s if missing, at most 7 days) and logs a single warning, because the service blocks clients that keep calling; use `noteAlmanacRateLimit` / `almanacRetryAfterSeconds` for any new Almanac fetch. Responses are cached permanently by portal code and galaxy through `almanac-store.ts`. `almanac-normalize.ts` adapts structured planet responses using their versioned English dictionary and the separate system endpoint, sharing metadata requests. Keep the legacy `lines.band`/`carries` display shape compatible with existing consumers and cached responses; normalize structured responses on cache reads and before writes. A 404 or an unavailable API must not block saving. `systemVerified` is reset when the address or galaxy changes.
- Flora, fauna, and mineral discovery counts belong to the planet, not the mission. Planet cards and their guide examples reuse the already-loaded Almanac data through `almanacDiscoveryCounts` (`src/lib/almanac/almanac-discovery-counts.ts`), without additional requests. Hide missing counts, keep zero visible, and never derive discovery totals from resource-list lengths.
- Planet cards and the planet detail modal share `PlanetDiscoveryCounts` (`src/components/shared/planet-discovery-counts.tsx`). In the modal, place the counters immediately before `planet-intro-code`, use the currently selected planet's data, and preserve the existing condition descriptions. Show Paradise when Almanac `paradise === true` and Dissonant when `lines.band.sentinels.ink === "exotic"`, consistently with the planet card (Paradise ribbon top left, Dissonant icon in the bottom-right indicator row); both labels may coexist and must update when switching planets.

The guide and `docs/manuale-utente.md` describe the badge.
- Planet card layout: the top-right corner is reserved for the **Visited** checkbox; the bottom-right row holds the indicators in this order: Dissonant icon, size, and a single water drop that fills up (empty when dry, a third Shallow, two thirds Ocean, full Deep). Do not put ribbons in the top-right corner.
- The leaderboard boards for stations, missions and planets visited carry the accent of their section (`accent`: `Orbit` blue `#6cb4ff`, `Crosshair` teal `#72d1c4`, `Eclipse` violet `#b48cf2`). The **Planets visited** board is fed by `readPlanetVisitCounts()`: it publishes only the number of planets per approved member, never which ones, counts every stored mark (even if the member can no longer mark that planet) and a read failure must not break the page.

- System facts (star, economy with stars, conflict dots, race icon) are built by `almanacSystemFacts()` and rendered by `components/shared/system-facts.tsx`, shared by the Planets system heading and the station cards. Race and economy stars have focusable tooltips, and `almanacWealth()` exposes the first economy mark for the Planets **Wealth** filter (Italian translations of Almanac values live in `translations/almanac-values.ts`; `translateAlmanacValue` falls back to a case-insensitive match, and the economy filter merges values that differ only by capitalisation; add any new Almanac word you see in a production select); the race tooltip sits on a wrapper because the icon itself is a CSS mask.

Don't edit it casually.
- **Specialty workflows (documented in `src/components/guide/guide-content.tsx`):**
  - A station cannot have multiple missions covering the same specialization. Treat the station/specialization association as unique, including coverage by multi-specialty missions; navigation must not introduce a mission picker or arbitrary priority rules for supposed duplicates. Any duplicates indicate invalid data or an enforcement bug, not a supported workflow.
  - Mission targets include `all`, `explorer_builder`, the individual member specialties, and `other`. An `all` mission covers Ranger, Explorer, and Builder tasks; `explorer_builder` covers Explorer and Builder tasks.

  - The guide's four mission workflows are: claim an available mission on Missions; create from a pending station; register one's own station and create from it; or filter Planets, follow the station link, and create from the station if its `+` action is available.
  - On Planets, the station link pulses when the current member could create a mission from that station, using the same role, station-ownership, and available-specialty rules as the station card's `+` action.

Do not make the conflicting change until they confirm. If the conflict is uncertain, inspect the relevant code and documentation first; do not treat requests that merely extend the rules as conflicts.

### Taxi service and member profiles

- `/taxi` and `/help-requests` share `request-board-route.tsx`, `HelpRequestsPage` and `messages/broadcast-request-handlers.ts`. Taxi requests use `/api/taxi-requests` and `subjectType: "taxi"` in the existing private-message document. Keep taxi, help and private-message feeds and thread operations isolated.
- All approved members may read requests and reply to active conversations. Creating a taxi request requires a valid NMS friend code, enforced server-side with `isValidNmsFriendCode`. Without it, the hero action opens My NMS Profile and the page explains the requirement. This restriction does not apply to replies.
- Authors may delete their own broadcast requests or replies; moderators/admins may delete any. Deleting a request removes all its replies. Simple view enforces user-level permissions. Private messages instead allow deletion by either participant or an admin, including descendant replies.
- Both broadcast boards have **In progress** / **Archived** tabs (Italian: **In corso** / **Archiviati**), with scoped counts. Requests without the optional boolean `archived` field remain active, preserving existing stored data.
- The request author, moderators and admins may archive or restore the entire root conversation through `PATCH /api/help-requests` or `PATCH /api/taxi-requests` with `{ id, archived }`. Enforce approved membership, effective-role/ownership checks and broadcast-kind isolation server-side. Reply authors cannot archive the root just because they own a reply; replies are not individually archivable. Simple view retains regular-user permissions.
- Archive/Restore appears after the date and before Delete, with a translated tooltip. Archiving preserves the root and all replies. Archived conversations are read-only for new replies: hide the reply button/form and reject reply submissions server-side with HTTP 409. Restore returns the conversation to In progress and enables replies again; existing deletion permissions are unchanged.
- Archived cards start collapsed, showing their heading, author, date and permitted actions. A keyboard-accessible chevron with `aria-expanded` and a translated tooltip expands/collapses the body and all replies. Returning to the Archived tab resets the cards to collapsed.
- Sidebar help/taxi counters include only active roots, never replies or archived requests. Dispatch the existing kind-specific `*-requests-changed` event after archive/restore so counters refresh. The station-detail help block reuses the same tabs, archive permissions and collapsed behavior; keep it available when matching requests exist only in Archived.
- Destination galaxy is required (stored 0–255, displayed 1–256). Both destination and meeting selectors use the same searchable combobox with a visible toggle, mouse/keyboard navigation and 16px input/option text. Arbitrary search text is not a valid choice.
- Meeting choices are Offline (default), arrange in replies, alliance hub (third, when configured), then all alliance stations, regardless of destination galaxy. `meetingPoint` distinguishes `offline`, `arrange`, `hub` and `station`. Older entries without it retain their saved station or mean arrange in replies.
- Resolve meeting coordinates server-side: station IDs against the station store, hub against `alliance.portalCode` and `alliance.galaxy`. Persist a snapshot so configuration changes do not move existing meetings. Reject unconfigured hubs and conflicting meeting-kind/station-ID payloads.
- Show meeting details after the request title, including the "Meeting:" prefix for Offline and arrange choices. Station links use the station blue (`#6cb4ff`) and Orbit icon. Link the hub only when an alliance station matches its galaxy and portal system (ignore the first glyph with `portalSearchMatches`); hide the portal code in the hub link label.
- The sidebar order is Taxi service, Messages, Help requests. Taxi and help counters count root requests, not replies; refresh on change events, visibility changes and the periodic interval.
- All approved members may see formatted friend codes (`formatNmsFriendCode`) in member profiles. Preserve separate restrictions on role, email and contact fields. `MemberProfileLink` opens the existing profile dialog from message participants and broadcast authors; without a message context the dialog is read-only and hides the message action.
- Keep the taxi guide examples illustrative and inert: hero button, request form, request with a reply, then read-only member profile with the friend code highlighted. Explain that either the requester or responder name opens their NMS profile.
- Dedicated taxi tests live in `tests/api/taxi-requests.test.ts` and `tests/pages/taxi-page.test.tsx`; also cover storage, route access, sidebar counters and guide examples in the existing matching suites.

### i18n

- Italian is the primary language and English is also supported. The locale is chosen client-side (browser language, then a selector stored in the browser), and URLs never change.
- `src/lib/translations.ts` merges the catalogs in `src/lib/translations/` (`en.ts`, `it.ts`, which is grouped by namespace). **Canonical keys are English strings.** A missing translation falls back to the key. Italian strings that are still used as keys in older components are mapped back automatically, and `aliases` in `it.ts` holds only extra legacy variants. Some keys are dotted ids (e.g. `missions.only_create_and_assign_your_specialty`).

## Concerns and TODO tracking

- `CONCERNS.md`: when you change code and notice something outside the task that looks wrong (a likely bug, a race, inconsistent docs, dead code, a security smell), don't fix it silently. Add an entry so it can be reviewed later. Each entry gets a short title, the file and line, what looks wrong and why, and the date. Before adding an entry, check that the concern isn't already listed.
- `TODO.md`: features and work that are still missing. Add an item when you find a gap.
- **IDs:** each entry heading starts with a unique ID made of a type prefix (`C-` for concerns, `T-` for TODOs) and 6 random lowercase alphanumeric characters, e.g. `## C-uu5uon: Title`. Generate the characters with `LC_ALL=C tr -dc 'a-z0-9' </dev/urandom | head -c 6` instead of making them up, because invented "random" strings repeat. Before using an ID, check that it doesn't appear in either file or in history (`git log --all --grep <id>`). IDs are never reused, even after an entry is removed. Refer to other entries by ID.
- **Commits:** a commit that addresses an entry references its ID in a trailer at the end of the message: `Fixes: C-uu5uon` when it resolves the entry, `Refs: T-v68hfw` for partial progress. Use one trailer per ID. In the same commit, remove a resolved entry from its file, or update it to show what remains.
